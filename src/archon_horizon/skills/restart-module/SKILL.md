## HomAlgDB rules

Read the repository root `AGENTS.md` before work. P-1: formalize the document's
objects, hypotheses, generality and statement order literally; a Mathlib counterpart
is metadata, never a replacement for the document's statement. P-2: follow the
document's proof route in the verbatim `## Proof`, its `[uses …]` annotations and
`deps.proof`; do not replace a difficult proof with a convenient stronger theorem.

Node headers are the source of truth. `blueprint/` and `hgraph/config.yaml` are
generated by `homalg blueprint-tex`; edit the node header, never generated `.tex`.
Build only through `horizon check` (the shared build lock); never invoke `lake build`
or `lake env lean` directly at the repository root. The task's explicit write scope
is binding: changes outside it are reverted. Preserve node IDs and paths.

Reviews use exactly `satisfactory`, `partial`, `mismatch`, `unverified`, or
`needs-adjudication`. Results the document uses without proving belong in `Cited_`
nodes. Send problems to the local inbox; open disputes with
`homalg dispute open <NodeId> --kind <kind> --reason "…"`. Do not open GitHub Issues
during a run. An unreadable page is `document-error`, addressed to `human` with
`--node <NodeId>` when known.

Read the tracked `horizon/review-policy.yaml` and repository
`docs/REVIEW_POLICY.md`. If independent agent reviews are explicitly enabled,
routine foundation, first-definition and explained-deviation reviews may proceed
through `homalg foundations review`, `homalg review-fidelity --session ...
--author-session ...`, and `homalg plan --early-review-ok --session ...
--author-session ...`. Actual author/reviewer sessions must differ; inspect source
evidence and record current hashes. Never invent an independent reviewer or treat
an agent verdict as human approval. Missing or disabled policy keeps the original
human review gates. Formalization sessions cannot change this policy themselves.

Only humans run `homalg dispute confirm`, `homalg dispute resolve`,
`homalg foundations confirm`, `homalg review-fidelity --human`,
`homalg transcription resolve`, or the early-review command without agent session
provenance. Agents must not create, replace or remove genuine human confirmations,
fidelity locks, transcription reviews, or confirmed/resolved dispute records.
Escalate unresolved mathematical or source disagreements; do not manufacture a
satisfactory review to advance a task.

Commit only to the engine ledger through `hgit` (`$HORIZON_GIT`). Never run
`git add`, `git commit`, or `git switch` against `<root>/.git`. Publishing uses
`homalg submit`; `homalg` manages the working branch. Keep private PDFs, page images,
page transcriptions and raw run logs out of public files and remote status data.

# Restart a module (clean rewrite)

Horizon should not fear refactoring. A **clean rewrite of a bad cone** is often
cheaper and more correct than another session of local patches on layered
abbreviations, instance packages, and `set_option` workarounds.

## When to restart instead of patch

Prefer a restart when several of these hold:

- The same elaboration / synthesis / equivalence failure returns after two or
  more fix attempts (AI looping on the same blocker).
- The file (or its import cone) ranks high on
  `"$HORIZON_BIN" benchmark -p <project> --json` — large summed
  `set_option maxHeartbeats` / `synthInstance.maxHeartbeats` budgets.
- Public API is a stack of needless `abbrev`s, index types, and
  `@[reducible]` transport lemmas that only exist because of the packaging.
- **Core definitions** fail [[definition-quality]] criteria: several independent
  consumers share the same encoding pain (dispatch
  `definition-quality-reviewer` when unsure).
- Naming and module layout diverge from [[mathlib-conventions]] enough that
  readers cannot reconstruct the statement from the name.
- The **blueprint route** and the Lean route disagree, and aligning them would
  rewrite most of the file anyway ([[blueprint-conventions]],
  [[strategy-convergence]]).

Do **not** restart a small, isolated lemma that only needs a correct proof.

## Depth diagnosis (do this first)

1. Run `"$HORIZON_BIN" benchmark -p <project> --details --json` and note the
   top files and which options they raise.
2. List the public API surface consumers import (search with [[leansearch]]).
3. Draw the dependency cone: which files must move together? Prefer the
   **smallest** cone that removes the layered debt.
4. State the target design in one short paragraph (mathlib-shaped names,
   flat structure, no decorative abbrevs). Preserve the node header and document route; a proposed route deviation requires
   an explicit dispute and recorded decision, not a quiet source rewrite.

## Backup, then rewrite

1. **Commit** any good work already in the tree (`project-git`).
2. **Backup** the cone before deleting or gutting it:
   - Preferred: `"$HORIZON_BIN" attempt save <files...> --reason "restart: <why>"`
     so the session dashboard keeps the dead end.
   - Also fine: copy under a short-lived path such as
     `.../Archive/Restart-<date>/` or a `*.lean.bak` next to the module **only**
     for the rewrite window.
3. Rewrite the module with a clean API:
   - Mathlib naming and module docstrings ([[mathlib-conventions]]).
   - Prefer inline types over one-off `abbrev` wrappers that force equivalence
     boilerplate.
   - Keep instance and morphism packaging shallow; one bundling layer beats three.
   - No new `set_option maxHeartbeats` unless a **measured** obligation remains
     after the redesign; treat remaining overrides as debt to file.
4. Point imports at the new surface; delete or stop exporting the old names.
5. Verify with [[lean-check]] (LSP loop, then `"$HORIZON_BIN" check`).
6. **Drop backups** once the new module builds and consumers are updated —
   git history already retains the old text. Do not leave permanent `*.bak`
   trees in the project.

## Blueprint and roadmap

- Node headers remain authoritative; regenerate the blueprint after lawful header changes.
  Never rewrite the document route simply because another proof is easier.
- Record the restart on the roadmap (`kind: refactor` is appropriate) and leave
  a short inbox `memory` when the failure mode is reusable.
